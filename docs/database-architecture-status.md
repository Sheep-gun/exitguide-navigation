# ExitGuide Navigation 데이터베이스 구조 및 구축 현황

ExitGuide Navigation의 데이터는 논리적으로 크게 두 개의 데이터베이스로 구성된다.

1. 사용자의 자연어 목적을 표준 기능으로 변환하는 **목적·기능 분류 DB**
2. 실제 Android 앱의 화면과 메뉴 이동 관계를 저장하는 **앱별 기능 그래프 DB**

---

## 1. 목적·기능 분류 DB

사용자가 입력한 자연어 문장을 ExitGuide가 탐색할 수 있는 표준 기능으로 변환하는 데이터베이스다.

### 분류 예시

| 사용자 입력 | 표준 기능 ID |
|---|---|
| 유튜브 프리미엄 끊고 싶어 | `subscription.cancel.entry` |
| 광고 문자 안 오게 해줘 | `marketing.settings` |
| 제주항공 가입하고 싶어 | `auth.signup.entry` |
| 내 계정을 없애고 싶어 | `account.delete.entry` |
| 배송지 바꾸고 싶어 | `address.manage` |

## 3. 두 DB의 연동 과정

```text
사용자 목적 입력
    ↓
목적·기능 분류 DB
    ↓
표준 목표 기능 확정
    ↓
현재 앱과 화면 인식
    ↓
앱별 기능 그래프 DB 조회
    ↓
현재 화면에서 가장 적합한 버튼 선택
    ↓
안전한 메뉴만 자동 탐색
    ↓
최종 목적지 발견
    ↓
사용자에게 최종 버튼 안내
    ↓
최종 결정과 클릭은 사용자가 수행
```

예를 들어 사용자가 `유튜브 프리미엄을 해지하고 싶어`라고 입력하면 다음과 같이 처리한다.

1. 목적·기능 분류 DB가 사용자 입력을 `subscription.cancel.entry`로 분류한다.
2. 앱별 기능 그래프 DB에서 유튜브의 화면과 버튼 정보를 조회한다.
3. 프로필, 구매 항목 및 멤버십, 멤버십 관리 등 목표와 연결될 가능성이 높은 메뉴를 탐색한다.
4. 구독 관리 또는 해지 화면을 최종 목적지로 판정한다.
5. 마지막 해지 확정은 사용자가 직접 수행한다.

## 4. 핵심 차이

| 데이터베이스 | 해결하는 질문 |
|---|---|
| 목적·기능 분류 DB | 무엇을 찾아야 하는가? |
| 앱별 기능 그래프 DB | 그곳까지 어떻게 이동하는가? |

두 데이터베이스를 결합하면 사용자의 자연어 목적을 이해하는 단계와 실제 앱에서 해당 기능을 찾아가는 단계를 분리할 수 있다. 이를 통해 앱별 버튼 이름이 다르거나 UI가 변경되더라도 표준 기능은 유지하면서 새로운 화면과 이동 관계만 갱신할 수 있다.

---

## 5. 현재 데이터의 해석과 과제

현재 앱별 기능 그래프의 통계에는 실제 서비스 앱뿐 아니라 테스트용 앱과 Android 시스템 화면도 포함되어 있다. 따라서 화면 746개와 버튼·메뉴 후보 13,523개가 모두 실사용 경로로 검증된 데이터라는 의미는 아니다.

또한 경로 후보 38개 중 37개가 검증 대기 상태인 `Shadow`이고 1개는 폐기·노후 상태인 `Stale`이다. 현재 완전히 검증된 운영 경로는 없으므로 앞으로는 단순히 버튼과 화면의 개수를 늘리는 것보다 다음 작업이 중요하다.

- 실제 앱에서 경로 후보를 반복 실행해 검증하기
- 성공한 경로를 `verified` 상태로 승격하기
- 앱 업데이트 후 기존 화면과 버튼의 유효성 재검증하기
- 중복 화면과 동적 콘텐츠를 정리하기
- 잘못된 버튼 선택과 무한 스크롤 사례를 실패 데이터로 축적하기
- 최종 목적지 도달률과 탐색 시간을 기준으로 그래프 품질 평가하기

즉, 현재는 데이터의 기본 골격과 대량 후보가 구축된 단계이며, 다음 단계의 핵심은 검증된 화면 이동 관계와 재현 가능한 성공 경로를 늘리는 것이다.
